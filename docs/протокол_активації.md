# Активація польових застосунків і підписані знімки (з 1.69.0)

> **Стан: у розробці, не застосовується.** Модуль «Активація застосунків»
> (адмінка → Модулі) типово вимкнений: без нього нові доступи не видаються,
> бази застосунків приймаються як звичайні, а знімки вже активованих телефонів
> — як і з увімкненим (1.70.2; дороги назад для телефона немає). Вмикати —
> після перевірки на телефонах; «лише підписані» — параметр `apps.signedOnly`.

Застосунок (РозкладкаС, В, Е, Д і наступні) не працює, доки InTrack не видасть
йому доступ. Доступ прив'язаний до конкретного телефона й конкретної особи;
знімок бази, вивантажений з телефона, читає лише InTrack і приймає лише від
телефона з чинним доступом. Мережі немає ні в застосунку, ні між ними й
InTrack: між ними — код телефона, QR-код (або файл) і файл знімка.

Тестові вектори — `app-activation-vectors.json` (ключі лише тестові);
еталонна реалізація — `backend/src/services/appActivation.js`
(`sealSnapshot` — сторона телефона).

## Порядок

1. Застосунок при першому запуску створює ключ **ECDSA P-256** у захищеному
   сховищі телефона (Android Keystore / iOS Secure Enclave, без експорту;
   типово — з вимогою відбитка чи PIN телефона на кожне підписання) і показує
   **код телефона**.
2. Особа передає код адміністраторові (особисто або з відомого номера).
3. InTrack: «Користувачі → картка особи → Доступ до застосунків» —
   застосунок + код → **QR-код активації** (той самий вміст — файл `.rza`).
   Нова видача в тому самому застосунку скасовує попередню («заміна телефона»).
4. Застосунок сканує QR-код (або відкриває `.rza`), перевіряє підпис InTrack
   і що `dev` = його власний код; показує особу, посаду й підрозділ лише для
   читання і починає працювати. Інший телефон той самий QR-код відхиляє.
5. «Зберегти знімок» дає файл `.rzs`, зашифрований для InTrack і підписаний
   ключем телефона.
6. InTrack («Звіряння → Імпорт бази з додатків») приймає `.rzs`, якщо доступ
   чинний; знімок телефона зі скасованим доступом — лише рішенням
   адміністратора. Перший прийнятий знімок закріплює відкритий ключ телефона.

## Код телефона

`SHA-256(відкритий ключ телефона, SubjectPublicKeyInfo DER)` → перші 55 біт
→ 11 символів Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, по 5 біт,
старші першими) + контрольний символ `ALPHABET[Σ (i+1)·індекс(символ_i) mod 32]`
(i від 0). Показується `XXXX-XXXX-XXXX`. При введенні: верхній регістр,
пробіли й дефіси прибираються, `O`→`0`, `I`/`L`→`1`.

## QR-код активації (`.rza`)

JWS compact, `{"alg":"ES256","typ":"RZA"}`, підпис ключем InTrack (P-256,
підпис r‖s, 64 байти, base64url). Вміст:

| Поле | Зміст |
|---|---|
| `v` | 1 |
| `aid` | ідентифікатор активації (UUID) |
| `app` | `rozkladka` (В) · `rozkladka_s` · `rozkladka_e` · `rozkladka_d` |
| `dev` | код телефона (12 символів, без дефісів) |
| `sub` | `{ id, name, position }` — особа з InTrack (ПІБ і посада — як записано в InTrack) |
| `dept` | `{ id, name }` — підрозділ InTrack |
| `iat` | коли видано |
| `scan_before` | до коли активувати QR-код: тиждень від видачі, виданий у січні — щонайменше до 20 січня |
| `exp` | кінець дозволу: 31 грудня 23:59:59 за Києвом року видачі |
| `by` | хто видав |

Застосунок перевіряє підпис **відкритим ключем свого InTrack** (вшивається у
збірку; `GET /api/app-activations/public-key`), `app`, `dev`, `scan_before` і `exp`;
зберігає `aid`, `sub`, `dept`. Таблиця `organization` заповнюється з `dept`.

**Дозвіл на трудовий рік.** QR-код — одноразовий дозвіл на апарат, як ліцензія:
у всіх діє до 31 грудня поточного року. Після `exp` застосунок не дає вносити
зміни й лише вивантажує знімок. Новий рік — новий дозвіл: адміністратор видає
QR-код на той самий телефон («Продовжити»), заздалегідь у грудні не видається;
активувати — у вікно 1–20 січня. Звільненому новий дозвіл просто не видають.
1–20 січня — інвентаризація, знімків не роблять.

## Знімок (`.rzs`)

```
RZS1\n
<JWS compact, typ "RZS", підпис ключем телефона>\n
<шифротекст бази SQLite>
```

Заголовок (вміст JWS):

| Поле | Зміст |
|---|---|
| `v`, `app`, `aid` | 1; застосунок; активація |
| `n` | лічильник знімків телефона, зростає (InTrack не приймає `n` ≤ попереднього) |
| `t` | час знімка (ISO) |
| `pub` | відкритий ключ телефона, SPKI DER, base64url |
| `epk` | разовий відкритий ключ P-256, SPKI DER, base64url |
| `iv`, `tag` | 12 і 16 байт AES-GCM, base64url |
| `sha256` | hex SHA-256 незашифрованої бази |

Шифрування: `ECDH(разовий закритий, відкритий InTrack)` →
`HKDF-SHA256(salt="RZS1", info=aid, 32 байти)` → **AES-256-GCM**, AAD = `aid`.

InTrack: перевіряє підпис заголовка ключем `pub`; розшифровує; звіряє
`sha256`; знаходить активацію `aid`: той самий застосунок, код від `pub` =
`device_code`, `pub` = закріпленому (якщо вже є), `n` > `last_counter`.
Підрозділ — з активації (назва в базі телефона не важить).

## Стан доступу

| Стан | Знімок |
|---|---|
| видано, бази ще не було | приймається; закріплює ключ телефона |
| працює | приймається |
| скасовано (заміна телефона / втрачено / інше) | лише рішенням адміністратора (той, хто керує користувачами) |
| знімок зроблено після `exp` (час `t` із підписаного заголовка) | лише рішенням адміністратора |
| доступу не видавали | не приймається |

Непідписані бази (`.db`) — лише РозкладкаВ і РозкладкаС, на час переходу.

## InTrack

- Ключ — `certs/apps/activation-key.pem`, у контейнері `/app/certs/apps/`,
  параметр `apps.activationKeyRef`; порядок — «Перший ключ» нижче.
- Таблиця `app_activations`; `actual_batches.activation_id`.
- `POST /api/app-activations` (видати), `GET /api/app-activations?user_id=`,
  `POST /api/app-activations/:id/revoke` (`replaced` | `lost` | `other`) —
  ті, хто керує користувачами, у межах свого обсягу.

## Перший ключ

Застосунок належить тому InTrack, чий відкритий ключ вшито у збірку. Ключ один
на робочий InTrack; стенд має власний, бойові збірки з ключем стенда не
випускаються. Робить адміністратор сервера під час розгортання, до першої
бойової збірки застосунків.

1. **Створити на основному сервері** (після збірки образів, із кореня
   репозиторію): `scripts/activation-first-key.sh`. Команда друкує відбиток і
   відкриту частину. Наявний ключ вона не змінює.
2. **Зберегти копію** закритого ключа `certs/apps/activation-key.pem` у сховищі
   секретів організації; ніде більше копій не тримати.
3. **Скопіювати той самий файл на резервний сервер** у `certs/apps/` і там
   запустити ту саму команду: відбиток має збігтися.
4. **Передати на збірку застосунків** відкриту частину (SPKI DER, base64) і
   відбиток: заміна `lib/src/issuer_key.dart` пакета `rozkladka_common` і
   перезбірка всіх застосунків. Відкрита частина не секретна.
5. **Перевірити:** адмінка → «Що ще не налаштовано» показує той самий відбиток.

**Заміна ключа** (витік чи втрата): видані дозволи стають недійсними, знімки
старим ключем не розшифруються. Новий ключ за кроками 1–5 (старий файл спершу
прибрати), нова збірка застосунків, нові QR-коди всім. Втрата ключа без копії —
те саме, тому крок 2 обов'язковий.
